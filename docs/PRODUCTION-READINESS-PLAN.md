- [x] **3.4 🅜 Batch-approve partial failure (new).** ✅ 2026-08-06. **This item's premise was wrong and the bug was worse.** The batch already used `Promise.allSettled`, so it did not abandon the rest on one failure — but it counted every settled promise as an approval, and `approveDraft` returns `awaiting_approvals` when a draft is short of its signatures. Also bounded to 4 concurrent — a "select all" of 60 held a transaction each against a PgBouncer pool of 25 and would have stalled every other screen in the factory. Logic extracted to `approve/batch.ts` with **10 unit tests**, since a counting bug in a component with no test infrastructure is a counting bug that comes back.

## Dependency map (why this order)

- Phase 1.1 (roles) blocks every new action in Phase 5 from shipping insecure — do it first; new actions adopt the pattern as they land.
- Phase 2.3 (typed results) is a prerequisite for gate UX in Phases 4–5; 2.5 (dates) touches files Phases 4–5 also touch — land it before them to avoid rebasing pain.
- Phase 3 (approve inbox tests) should precede Phase 6.4+ — a real provider multiplies traffic through exactly that untested funnel.
- Phase 5.7 unblocks 7.1. Phase 6.1 is independent and small — it can be pulled forward any time.
- Phases 0 and 6.1–6.2 are the cheapest honest wins; nothing depends on them being late.
